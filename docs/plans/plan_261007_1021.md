# Plan: EmbeddingGemma 2 Integration

**Date:** 2026-10-07 10:21
**Status:** Implemented (2026-10-07); end-to-end ONNX verification remains opt-in and is tracked by the integration test.

## Objective

Add a supported, local ONNX integration for Google's latest open EmbeddingGemma 2 model while preserving the existing `ElBruno.LocalEmbeddings` behavior and package compatibility.

EmbeddingGemma 2 is a 740M-parameter multimodal model with a 270M text backbone, a shared 768-dimensional embedding space, an 8,192-token context window, and Matryoshka dimensions of 128, 256, 512, and 768. Its text, image, audio, and video paths have different preprocessing needs. The current core generator accepts strings and its tokenizer is BERT/vocab.txt-specific, so this model should not be treated as a drop-in change to the core default.

## Proposed Scope

Deliver a dedicated `ElBruno.LocalEmbeddings.EmbeddingGemma` companion package for local **text embeddings** first, using a compatible ONNX export and the existing Microsoft.Extensions.AI `IEmbeddingGenerator<string, Embedding<float>>` abstraction.

Keep image, audio, and video input support as a separate follow-up milestone. Do not advertise full multimodal support until modality-specific preprocessing, API shape, and ONNX model dependencies have been verified and implemented. Existing generic core behavior and the default model remain unchanged.

## Phase 1: Verify the Inference Contract

Before committing to a model export or public API:

1. Pin and inspect a specific revision of the candidate ONNX export (initial candidate: `onnx-community/embeddinggemma-2-ONNX`); do not download mutable `main` artifacts in production.
2. Inspect the text ONNX graph inputs, outputs, dynamic/static axes, data types, pooling behavior, output normalization, and external tensor-data dependencies.
3. Confirm the Gemma 4 tokenizer implementation and special-token behavior using the export's `tokenizer.json` and `tokenizer_config.json`. Verify compatibility with `Microsoft.ML.Tokenizers`; do not reuse `HarrierTokenizer` without proving equivalent normalization and token IDs.
4. Run reference comparisons against Google's documented Sentence Transformers inference for representative short, long, multilingual, code, and task-prefixed inputs.
5. Verify the exact export's license and redistribution terms, quantized file support, sizes, and checksums. Record the pinned revision and verified file manifest in the implementation documentation.

**Gate:** Proceed with the ONNX integration only if repeatable reference parity and stable model file distribution can be established. Otherwise, document the incompatibility and evaluate a separate inference backend rather than silently shipping an unverified export.

## Phase 2: Add the Text-Only Companion Package

Create `src/ElBruno.LocalEmbeddings.EmbeddingGemma/` following the existing Harrier companion-package conventions:

1. Add a `net8.0;net10.0` package project referencing the core library and using ONNX Runtime and Microsoft.ML.Tokenizers consistently with the repository.
2. Implement `EmbeddingGemmaTokenizer` for the verified tokenizer format, including Gemma special tokens, padding, truncation, the 8,192-token limit, and cancellation-aware batch tokenization.
3. Implement `EmbeddingGemmaOnnxEmbeddingModel` for the verified ONNX graph contract. Pool only if required by the graph; apply the expected normalization and optional Matryoshka truncation in the documented order.
4. Implement options for model repository/revision, local model path, cache directory, download behavior, sequence length, task prompt, output dimensions, quantization choice if verified, normalization, and ONNX thread settings. Validate option values and keep safe, documented defaults.
5. Implement a model downloader that retrieves only the required text graph, external data, and tokenizer/configuration files. Validate required files, cache integrity, cancellation, and concurrent-download behavior; never accept untrusted local paths outside the configured cache when resolving downloaded model files.
6. Implement `EmbeddingGemmaEmbeddingGenerator` as `IEmbeddingGenerator<string, Embedding<float>>`, with async creation, metadata, batching, and disposal patterns consistent with Harrier and core.
7. Support task steering without changing caller text implicitly in surprising ways: expose a clear prompt option/helper for query/document prefixes, document the exact prefix formats, and test consistency for both sides of retrieval.

## Phase 3: Tests and Integration

1. Add `src/Tests/ElBruno.LocalEmbeddings.EmbeddingGemma.Tests/` and include it in `LocalEmbeddings.slnx`.
2. Add deterministic unit tests for tokenizer special tokens, truncation, batch padding/masks, prompt construction, dimension truncation/normalization, downloader file selection and validation, options, and DI registration.
3. Add ONNX contract tests using a small checked-in synthetic fixture where practical; do not check in downloaded production weights.
4. Add opt-in model integration tests that download/use a pinned revision and compare output dimensions, finite values, normalization, and cosine-similarity ordering with reference fixtures. Mark network/model-dependent tests as requiring external resources and keep standard tests offline.
5. Test both target frameworks and verify the package remains trimming/AOT-compatible if the implementation claims those properties.
6. Update the solution and relevant test/build configuration without changing unrelated projects.

## Phase 4: Documentation and Release Readiness

1. Add package README and update root README with a concise text-only EmbeddingGemma 2 quick start, package installation, model download size/cache expectations, hardware requirements, and local/offline behavior.
2. Add `docs/embeddinggemma-integration.md` with setup, task prefixes, dimensions, context limits, model revision/license details, quantization caveats, cache management, and troubleshooting.
3. Update `docs/api-reference.md` and `docs/configuration.md` for any public APIs and options introduced.
4. If a new packable project is added under `src/`, update `.github/workflows/publish.yml` and `docs/publishing.md` in the same implementation change.
5. Run targeted tests, then `dotnet build` and `dotnet test` from the repository root before release.

## Follow-Up: Multimodal Inputs

After the text package is stable, assess a separate typed-input API for image, audio, and video. This follow-up must verify the export's modality encoders and external tensor files, preprocessing requirements, payload size/resource limits, cancellation, and whether a usable .NET image/audio/video processing dependency is justified. Preserve text API compatibility and avoid forcing multimodal dependencies on text-only consumers.

## Acceptance Criteria

- Consumers can generate local EmbeddingGemma 2 text embeddings through the established Microsoft.Extensions.AI abstraction without changing the existing core default.
- Default output is the model's verified 768-dimensional result; supported truncation dimensions are validated and correctly normalized according to Google's guidance.
- Task prompts, tokenizer behavior, sequence limits, batching, and model graph processing match reference inference within a documented numerical tolerance.
- Downloaded models are revision-pinned, cache safely, and include all required external tensor data; offline/local-path usage is documented.
- Unit tests run without network access, and model-dependent integration coverage is opt-in.
- Package, API, model-source, license, and publishing documentation are complete.
- Multimodal behavior is clearly marked unsupported until its follow-up milestone meets its own acceptance criteria.

## Risks and Open Decisions

- **ONNX export stability and parity:** The available ONNX export is community-maintained. A pinned revision and explicit parity gate are prerequisites.
- **Tokenizer fidelity:** Gemma 4 tokenization and preprocessing differ from the current BERT tokenizer and need direct validation.
- **External weights and package size:** ONNX graphs rely on separately distributed weight data; incomplete download handling will produce load-time failures.
- **Model size and hardware:** Even the text-only path is materially larger than the default MiniLM model; documentation should set realistic memory and startup expectations.
- **Prompt API design:** The current generator abstraction receives strings without query/document roles. Decide whether to expose role-specific methods/helpers, an options-level prefix, or a companion API while preserving ordinary `GenerateAsync` semantics.
- **First release modality scope:** This plan proposes text-only support first and multimodal support as follow-up; confirm this scope before implementation if full multimodal support is required in the initial release.
